# 팀 공용 작업 가이드

개발자와 AI의 공통 지침임. 최신 사용자 요청과 팀에서 확정한 설계·API 명세를 우선함.
미정인 사항을 임의로 확정하거나 준비 중인 기능을 완료했다고 보고하지 않음.

## 프로젝트 기준

- SwiftUI, 최소 iOS 17.0, 라이트 모드 고정임. 새 API의 지원 버전 확인 필요.
- 프로젝트: `39-SOPKATHON-iOS/39-SOPKATHON-iOS.xcodeproj`
- 소스: `39-SOPKATHON-iOS/39-SOPKATHON-iOS/`
- 프로젝트 경로와 이름은 `SOPKATHON` 표기를 사용함. 경로 변경 시 빌드 설정도 함께 갱신함.

## AI 사용 원칙

참고: [솝커톤 iOS AI 플레이북](https://sopkathon-ios-ai-playbook.ratedkid4.chatgpt.site/#slide-9)

### 질문과 설계

- 동작·데이터·설계·범위·완료 기준에 영향을 주는 불확실성은 추측하지 않고 질문함.
- 관련 코드·명세·기존 합의를 먼저 확인하고, 이미 확인했거나 확정한 내용은 다시 묻지 않음.
- 모호함이 남으면 답변에 따라 꼬리질문함. 한 번에 핵심 한두 개와 결정에 미치는 영향을 설명함.
- 침묵이나 모호한 동의를 요구사항 확정으로 간주하지 않음.
- 명확한 요구사항과 기존 규칙 안의 구현 세부는 직접 결정함.
- 새 기능·동작 변경은 관련 호출·데이터·상태 흐름과 변경 파일·이유를 먼저 설명함.
- 입력·API·화면 전환·상태 관리·실패·중복·취소·재시도·복구는 해당 기능에 필요한 범위만 설계함.
- 설계가 미정이면 “그냥 해줘”, “바로 구현해줘”라고 해도 질문부터 진행함.
- 사용자가 이해하고 확인한 설계에 따라 작게 구현함. 명확한 설계의 승인을 반복 요구하지 않음.

### 탐색과 작업 범위

- 작업 전 Git 상태를 확인하고 사용자의 미커밋 변경을 덮어쓰거나 삭제하지 않음.
- 요청 대상 파일과 직접 의존하는 코드부터 확인하고, 원인·영향 확인에 필요할 때만 탐색을 확장함.
- 단순 수정·문서 작업에서 전체 파일을 나열하거나 읽지 않음. 변경·추가 확인 필요가 없으면 재조회하지 않음.
- 기존 구조·공통 코드를 활용해 요구사항을 충족하는 가장 단순한 구현을 우선함.
- 요청하지 않은 기능·설정·라이브러리·계층·프로토콜이나 미래를 위한 추상화를 추가하지 않음.
- 실제 중복이나 현재 요구사항이 있을 때만 공통화하고 무관한 리팩토링·파일 이동·스타일 정리를 하지 않음.
- 범위 확대가 필수면 이유·영향·최소 대안을 설명하고 사용자와 범위를 확정함.
- 공통 인터페이스 변경 전 사용처를 확인하고 다른 담당 기능·기획·디자인·서버에 미치는 변경을 공유하도록 안내함.
- 오류는 재현 조건·로그·관련 코드부터 확인함. 가설과 근거를 구분하고 추측으로 광범위하게 수정하지 않음.

### 구현 후 설명

- 추가·수정·삭제한 내용, 변경 이유와 동작 영향을 간단한 한국어로 설명함.
- 변경 코드 파일은 절대 경로의 클릭 가능한 Markdown 링크로 제공하고 핵심 위치의 실제 줄 번호를 연결함.
- 형식: `[파일명](/절대/경로/파일.swift:줄번호)`. 공백이 있는 경로는 링크 대상을 `< >`로 감쌈.
- 링크와 함께 실제 핵심 변경 코드를 보여줌. 수정은 전후 또는 diff, 새 코드는 주요 구현·사용 예시로 설명함.
- 전체 파일을 불필요하게 복사하지 않고 담당 기능의 연결·실행 흐름을 이해할 수 있게 설명함.
- 막히면 시도·결과·원인 가설·근거·필요한 도움을 구분함. 개인 대화·무관한 개인정보는 문서에 넣지 않음.

## 구조와 구현 기준

- `Application`: 앱 진입점, `Data/Network/Base`: 공통 통신, `Data/Network/DTO`: 요청·응답 DTO임.
- 화면은 `Presentation/<화면>/Model·View·ViewModel`, 공통 UI·확장·리소스는 `Presentation/Common`에 둠.
- 화면 전용 UI는 해당 화면에 두고 실제 공유할 때만 Common으로 이동함.
- View는 UI·이벤트 전달, ViewModel은 화면 상태·처리를 담당함. View에서 요청을 직접 구성하지 않음.
- UI 상태는 메인 액터에서 변경하고, DTO와 화면 모델은 역할이 다를 때 분리함.
- 필요한 로딩·빈 데이터·실패·취소 상태를 처리하고 로딩은 성공·실패 모두에서 해제함.
- 빈 폴더는 `.gitkeep`으로 유지하되 앱 리소스 복사 대상에서 제외함. 실제 파일 추가 후 제거 가능.
- `Info.plist`는 빌드 설정에서 참조하며 Copy Bundle Resources에 포함하지 않음.

## Figma와 리소스

- Figma 연결·기준 지정 시 해당 디자인 지침·설계서·컴포넌트·토큰을 우선 적용함.
- 색상·폰트·여백·정렬·안전 영역·선택 상태·스크롤·탭바·화면 전환을 확인하고 임의의 유사 디자인으로 대체하지 않음.
- 요구사항·기존 코드와 충돌하거나 디자인이 불명확하면 질문함. 구현 화면과 비교하지 못했으면 미확인으로 보고함.
- 폰트는 `Presentation/Common/Extension/Font+.swift` 사용. 공통 스타일은 디자인 확정 후 수정함.
- 색상·이미지는 기존 Assets를 우선 활용하고 중복 생성하지 않음.

## 네트워크

- URLSession·async/await 기반 `BaseService` 사용. `EndPoint`에서 경로·메서드·쿼리·헤더 정의함.
- API 연동 전 성공 코드·응답 DTO·디코딩·콘텐츠 타입·인증을 서버 명세와 맞추고 완료한 TODO는 제거함.
- 주소는 `BASE_URL`로 전달함. xcconfig는 Git 제외 대상이며 필요한 키·설정 방법만 공유함.
- 주소·토큰을 하드코딩하지 않고 비밀값을 커밋하지 않음. 로그에도 토큰·개인정보를 노출하지 않음.
- 통신·HTTP·디코딩·취소 오류를 구분함. 새 네트워크 라이브러리는 팀 합의 없이 도입하지 않음.

## 코드 컨벤션

새 코드와 수정하는 코드에 아래 규칙 적용함. 컨벤션 적용만을 위한 무관한 코드의 일괄 수정은 지양함.

### 네이밍과 선언

- 타입·클래스·구조체·enum·프로토콜은 UpperCamelCase 사용. extension도 대상 타입명 유지함.
- 함수·변수·상수·enum case는 lowerCamelCase 사용.
- 역할과 책임이 드러나는 이름 사용. 불필요한 약어 지양함.
- URL·ID·API·DTO는 대문자로 표기하되 이름 맨 앞에서는 소문자로 시작함.
  예: `userID`, `profileURL`, `urlString`.
- Bool은 `is`, `has`, `can`, `should` 등으로 상태를 표현함.
- 함수는 동사로 시작하고 호출부에서 자연스럽게 읽히도록 작성함.
- 변경하지 않는 값은 `let` 우선 사용. 변경이 필요한 경우에만 `var` 사용함.
- 타입이 명확하면 타입 추론 사용. 빈 배열·초기값 없는 옵셔널은 타입 명시함.
- 화면의 부모 View에만 `View` 접미사 사용함.
- 자식 UI는 `View` 접미사 없이 부모 화면과 역할이 드러나도록 네이밍함.

### 접근 제어와 프로토콜

- 타입 내부에서만 쓰는 속성·메서드는 `private` 사용함.
- 외부에서 읽기만 허용하는 속성은 `private(set)` 사용함.
- 상속하지 않는 클래스에는 `final` 사용함. 불필요한 `public`, `open` 지양함.
- 부가적인 프로토콜 채택과 구현은 extension으로 분리하고, extension 하나에 프로토콜 하나씩 작성함.
- SwiftUI의 `View`, `App` 등 타입의 핵심 역할을 정의하는 프로토콜 채택과 구현은 본체에 둠.
- 저장 속성·override 메서드 등 extension에 작성할 수 없는 코드는 본체에 둠.
- 컴파일러가 합성하는 프로토콜 구현은 합성 가능한 위치에 선언함.

### 레이아웃과 공백

- 들여쓰기는 공백 4칸 사용함.
- 줄 길이는 90자 이내 권장, 최대 99자로 제한함.
- 콜론 오른쪽, 쉼표 뒤, 연산자 양옆에 공백 사용함.
- 연산자 오버로딩 함수는 연산자와 여는 괄호 사이에 공백 한 칸 사용함.
- 긴 함수 정의·호출은 파라미터 단위로 줄바꿈함.
- 클로저 파라미터가 2개 이상이면 길이와 관계없이 파라미터별 줄바꿈함.
- 긴 `if let`·`guard let` 조건은 줄바꿈하고 들여씀. `else`는 `guard`와 같은 깊이로 정렬함.
- 함수 사이에는 빈 줄 하나 사용함.
- 타입·extension 스코프의 맨 위와 아래에는 빈 줄 하나 사용함.
- 함수 내부 시작·끝에는 불필요한 빈 줄을 넣지 않음.
- MARK 위아래에는 빈 줄 사용함. 불필요한 MARK는 제거함.
- `@objc`는 함수 선언과 줄을 나눠 작성함.
- 빈 줄의 공백 제거. 파일 끝에는 개행을 남김.

### Import와 주석

- 내장 프레임워크를 먼저 import하고, 빈 줄 뒤에 서드파티 라이브러리 import함.
- 각 그룹 안에서는 알파벳순으로 정렬함. 사용하지 않는 import 제거함.
- 파일 헤더의 파일명·프로젝트명·작성자·작성일을 실제 정보로 작성함.
- 기존 타인의 작성자명은 변경하지 않음.
- 설명 주석은 간단한 음슴체 사용. 예: `// TODO: 서버 명세 확정 후 경로 추가 필요.`
- 불필요한 주석은 제거하고 변경 설명은 PR에 작성함.
- 추가 구현이 필요한 TODO와 코드만으로 알기 어려운 제약·이유는 남길 수 있음.
- 다른 프로젝트의 경로·도메인·인증값·응답 규칙을 그대로 가져오지 않음.

### 옵셔널과 클로저

- 강제 언래핑 지양함.
- 값이 없으면 종료할 때는 `guard let`, 값이 있을 때만 실행할 때는 `if let` 사용함.
- `??`는 의미 있는 기본값에만 사용함. `userID ?? 0`처럼 임의의 값으로 오류를 숨기지 않음.
- 짧고 명확한 클로저는 `$0` 사용 가능. 복잡한 조건은 인자 이름 명시함.
- `[weak self]`는 순환 참조 가능성이 있는 경우에만 사용함.
- 이름 구분·클로저 문법상 필요한 경우 외에는 불필요한 `self` 지양함.

### SwiftUI와 비동기 처리

- `body`에서 화면 전체 구조가 보이도록 작성함.
- 독립적인 역할의 UI는 별도 View 타입으로 분리함.
- 간단한 화면 전용 UI는 계산 속성으로 분리 가능함.
- 내부에서만 사용하는 상태에는 `private` 사용함. 상태 관리 방식은 기존 설계 따름.
- UI 상태 변경은 메인 액터에서 처리함.
- 오류를 조용히 무시하거나 빈 catch를 두지 않음.
- `try?`는 실패를 무시해도 되는 경우에만 사용함.
- 로딩 상태는 성공·실패 모두에서 해제함. 필요 시 `defer` 사용함.
- 화면과 연결된 비동기 작업은 취소 처리도 고려함.
- 개발 중 Preview 사용 가능. PR 전 Preview 코드와 미사용 Preview 전용 목업 제거함.
- 미사용 코드·주석 처리한 코드 제거함.
- 의미가 불분명한 숫자·문자열의 반복 사용 지양함. 기존 공통 색상·폰트·간격 정의 우선 사용함.
- 불필요한 print는 push 전 제거함.

## 상세 컨벤션 확인 범위

[팀 상세 컨벤션](docs/CONVENTIONS.md)은 아래 작업에 해당하는 항목만 확인함. 매번 전체 문서를 읽지 않음.

- 폴더 추가·리소스 변경: 폴더 구조, 폰트와 리소스, 이미지 에셋 컨벤션.
- Swift 코드 추가·수정: 이 문서의 코드 컨벤션 적용. 추가 예시가 필요한 경우에만 상세 문서의 코드 예시 확인함.
- 커밋·브랜치·PR·머지: Git 컨벤션, PR·머지 체크리스트.
- 문서만 수정할 때는 코드·에셋 컨벤션을 추가 조회하지 않음. 주석 수정은 이 문서의 주석 규칙만 적용함.

## Git 핵심 규칙

- 커밋은 `[태그] #이슈번호 - 작업내용`, 브랜치는 `태그/#이슈번호` 형식임. 작업별로 커밋함.
- 새 브랜치는 최신 main 기준으로 생성하되 기존 브랜치에서 이어가는 요청이면 해당 브랜치 사용함.
- 커밋·푸시·PR·머지·브랜치 삭제는 현재 요청의 허용 범위까지만 수행함. 타인의 이력을 임의로 재작성하지 않음.
- PR 템플릿을 사용하고 리드 승인 후 머지함. 머지 완료 후 작업 브랜치 삭제함.
- 카카오톡 공유는 팀원의 협업 절차이며 AI 메시지 전송은 명시적으로 허용된 경우에만 진행함.

## AI 검증과 보고

- 변경 규모·위험에 맞는 최소 검증부터 기존 빌드·테스트·로그 수단으로 실행함.
- 검증만을 위해 요청하지 않은 도구·테스트 환경·문서를 추가하지 않음. 문서·주석 변경에 불필요한 전체 빌드는 하지 않음.
- 실패 시 종료 코드·오류 로그로 원인과 이번 변경의 관련성을 확인하고 범위 내 수정 후 영향받는 검증을 재실행함.
- 같은 실패를 분석 없이 반복 실행하지 않음. 기존 오류·환경 문제는 근거·영향·미검증 범위를 보고하고 범위 밖 수정은 확인함.
- 정상·실패·중복·취소·재시도는 해당 기능에 필요한 범위에서 확인함.
- 도구 접근 불가·테스트 부재·미실행을 통과로 처리하지 않음.
- 빌드 성공·화면 확인·실제 서버 확인과 미확인 항목을 구분함. iOS 17 설정만으로 기기 실행을 확인했다고 보고하지 않음.
- 완료 보고에 실행 명령 또는 확인 방법·결과·필요한 로그와 결과 파일 링크를 남기고 비밀값·개인정보는 제외함.
